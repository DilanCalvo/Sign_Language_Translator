# Web version — ASL letters, numbers & words in the browser

Web app that recognizes ASL in real time from the camera, with a
Letters / Numbers / Words toggle: static letters (A–Y, no J/Z), digits (0–9),
and dynamic **word signs** (a temporal TCN over both hands + body position).
Same models, same math as the desktop app — it runs 100% in the browser: no
backend, no video ever leaves the device.

Beyond recognition, the app is a **two-way conversation bridge**: recognized
signs are spoken out loud (Web Speech synthesis, voice picker + on/off), the
hearing side types or dictates back (their message pops up large over the
camera), everything lands in a chat panel, and a REC toggle keeps an
exportable transcript (TXT + CSV, byte-compatible with the desktop app's
`logs/` files) that follows the conversation across all three modes.

## Run locally

```bash
cd web
python -m http.server 8000
# open http://localhost:8000            (the app)
# open http://localhost:8000/js/utils.test.html   (the parity test gate)
```

Camera works on `http://localhost` (secure-context exception). On any other
host it requires HTTPS — Netlify provides that automatically.

## Architecture (one screen, vanilla JS, no build step)

```
index.html          UI: header (mode toggle + voice/settings/help), camera stage
                    with overlays (prediction bug, caption strip, REC lamp, big
                    incoming message), conversation panel (chat + compose bar),
                    help/settings <dialog>s
css/style.css       Design system: tokens (caption-yellow on near-black), the
                    caption-console look, mobile-first responsive layout
js/config.js        Shared tunables. Model/threshold values COPIED from
                    ../config.py (rule 3 below); smoothing/cadence values are
                    TIME-BASED ms (deliberate web divergence — see below)
js/modes.js         Per-mode descriptors (kind, model URL, labels URL, acceptance
                    threshold, UI copy) — the ONLY things that differ between
                    modes. `kind` routes pipeline.js: "static" vs "sequence"
js/utils.js         Port of normalize_landmarks + the word helpers
                    (buildWordFeatures / wordFeaturesFromRaw / resampleSequence),
                    plus the time-based TimeSmoother / CharBuffer (with
                    fingerspelled word-close) / WordCommitFSM / WordBuffer
js/model.js         DenseModel (letters/numbers: Dense+BatchNorm) and TCNModel
                    (words: Conv1D causal-dilated + GlobalAvgPool + Dense), both
                    plain-JS forward passes (no TF.js — its converter does not
                    install on Windows). Outputs are model-owned reused buffers:
                    valid only until the next predict() — copy to keep
js/pipeline.js      camera → mirrored canvas → MediaPipe hands (+ pose in words)
                    → features → active model → smoother/FSM → UI, per mode;
                    hooks voice + conversation + commit flash on commit frames
js/tts.js           Voice output (Web Speech synthesis): voice enumeration, iOS
                    gesture unlock, prefs (enabled / voice / letters speak
                    per-word-or-per-letter). Counterpart of src/voice.py
js/stt.js           Dictation for the hearing side (SpeechRecognition,
                    feature-detected; mic hidden where unsupported)
js/conversation.js  Conversation store + REC flag + TXT/CSV export formatters
                    (byte-compatible with src/conversation_log.py files)
js/ui.js            Chat panel, compose bar, big message, dialogs, voice
                    controls, commit feedback (flash + vibration)
js/prefs.js         localStorage helper ("asl-web." namespace)
js/utils.test.html  THE GATE: replays fixtures (all modes) generated from real
                    capture data + behavioral tests (fake clocks) + export
                    format tests; everything must be PASS
model/              letters/ + numbers/ + words/ model_weights.json + labels +
                    hand_landmarker.task + pose_landmarker_lite.task (local copies)
vendor/mediapipe/   Vendored @mediapipe/tasks-vision@0.10.14 (ESM bundle + WASM)
vendor/fonts/       Vendored variable fonts (Inter, Google Sans Code) — no CDN
fixtures/           letters (root) + numbers/ + words/ input→expected-output
                    pairs generated by tools/make_fixtures.py
```

**Time-based thresholds (deliberate divergence from config.py, 2026-07-19).**
The desktop counts FRAMES for smoothing windows/cooldowns because its camera
rate is fixed. The web runs anywhere from ~15fps (phone, pose active) to 60fps,
so frame counts made phones need ~3x longer sign holds in wall-clock time.
`js/config.js` therefore expresses every smoothing/cadence threshold in
MILLISECONDS (each value = its config.py twin at the 30fps baseline), and
`TimeSmoother`/`CharBuffer`/`WordBuffer` take the frame timestamp as an
explicit parameter (deterministic in tests). Same real-time feel on every
device; desktop behavior unchanged at 30fps.

**Words mode differs from the static modes** (it is a separate per-frame branch
in `pipeline.js`, not the `classify()` path): it tracks **two hands** by
handedness plus the **shoulders** (a MediaPipe pose detector, created lazily on
first entry to Words), builds a body-anchored 130-value feature per frame, keeps
a rolling buffer, and only runs the TCN while the hands are **moving**
(a motion gate). A recognized sign is committed through a vote → confirm →
2-second lock-out state machine and appended to the sentence strip, which
auto-clears after a pause. The pose `.task` adds ~5.5 MB and pose runs only in
Words mode, so letters/numbers pay nothing for it.

## The four parity rules (breaking any of these = silent wrong predictions)

1. **Mirror before detection.** The desktop app flips the frame BEFORE
   MediaPipe (`src/detector.py`: `cv2.flip(frame, 1)`), so the whole dataset
   was captured on mirrored video. The web app draws the camera onto a
   mirrored canvas and feeds THAT to the landmarker. If predictions are
   garbage while the hand is detected fine, suspect this first.
2. **The math in `js/utils.js` must match `src/utils.py` exactly** —
   `normalizeLandmarks`, `buildWordFeatures`, `resampleSequence`,
   `sequenceMotion`. Never edit one without the other, and never trust the
   port by eye — run the test gate. (The smoothing/buffer CLASSES are
   deliberately time-based here — that divergence is documented above and
   covered by the gate's behavioral sections instead.)
3. **`js/config.js` model/threshold values are copied from `config.py`.** If
   you tune one in either place, change the other too (each constant's comment
   names its `config.py` twin). The ms-based smoothing constants map to their
   config.py frame twins at 30fps.
4. **The MediaPipe runtime and `.task` model are local and version-pinned.**
   Never switch to a CDN copy or bump the version casually: a different
   detector version can produce subtly different landmarks than the ones the
   training data was captured with.

## After retraining a model

One command regenerates everything the web app consumes for a mode — export
weights, regenerate parity fixtures, copy the labels (and, for words, copy the
pose `.task` the first time):

```bash
venv/Scripts/python tools/update_web.py letters
venv/Scripts/python tools/update_web.py numbers
venv/Scripts/python tools/update_web.py words
```

Then open the test gate and confirm **ALL TESTS PASS** before deploying (the
one gate covers all modes). Skipping this leaves the deployed site silently
serving the old model.

## Deploy

`netlify.toml` (repo root) is already configured: connect the repo in the
Netlify UI and every push deploys `web/` with sane cache headers (model/JS
revalidate on every visit; the vendored runtime is cached forever).
